# AMoDE engineering rules

Apply these rules in every conversation and worktree for this repository. Read the AMoDE Agent prompts and use the sections that match the request. Read the relevant application contracts, pinned toolchain settings and available CI. For presenter-laptop operations, also read the AMoDE workspace's `AGENTS.md` when available and follow its classroom startup and restart instructions. [README.md](README.md)

## Before implementation

- Locate the Git root, confirm the authorized feature branch and inspect existing changes and the index. Preserve user work and original course material. Keep `main` empty until an authorized reviewed merge. Never push directly to `main` or recover code through reset, restore, revert, historical checkout, history rewriting or force pushes.
- Before downloading files or running tools that generate files, check the current `.gitignore` and Git Workflow §2.1. Identify actual data, model, output, credential and device-configuration paths. Identify files already tracked or staged. Use confirmed paths for ignore edits, and use `git check-ignore --no-index -v` to verify ignored files and retained sources or fixtures. Untracking needs a separate request. ## Architecture checks

- Use FMS (PyQt), Admin (PyQt), and the User App (Android) as the default AMO clients. Admin (Web) is an unofficial companion client.
- When implementing or changing an Admin (PyQt) feature, include the equivalent behavior in Admin (Web) in the same work scope. Plan both clients from the start and verify the affected workflow on each before considering the feature complete.
- Map the affected component, owner, direction and protocol to the appropriate Main or Dev view and interface. The current interface specification and meeting record assign IF-03 TCP to AMO FMS and a separate Web Service HTTP API to AMO Admin. The linked SW drawing labels the TCP screen AMO Admin. Flag that discrepancy and preserve the implemented client boundaries until the team resolves it. Keep DB access in Main Control and treat the Android HTTP demo path as a development path. [Meeting record](https://k8c1.atlassian.net/wiki/spaces/K8C1sesac/pages/9142410)
- Map the current state, event, guard, next state and required physical evidence. Keep command acceptance, observed vehicle state, facility occupancy and eligibility for another dispatch distinct. Treat 70% as the charging-to-idle guard and apply route energy, connection and facility checks separately. Check the latest agreements for taxi boarding, rental start and expiry, and Cargo handoff and detachment. Surface ambiguous or conflicting transitions before implementing them.
- Keep motion disabled by default. Report simulated behavior and physical integration results separately. Use Python 3.12 and ROS 2 Jazzy on Ubuntu 24.04 for ROS integration.

## Verification and Git

- Split work by purpose and dependency into independently verifiable stages. Include related code, contracts and tests. Run the applicable formatter, lint, line-count, build and test checks for each stage, and record commands, outcomes and skipped checks.
- When commits are requested, stage only the verified stage using explicit paths or selected hunks. Preserve unrelated staged work. Review `git diff --staged` for correctness, scope, oversized files and sensitive material. Verify that the stage works without later unstaged changes. Make one English Conventional Commit per verified stage and report its ID and results.
- When a push or PR is requested, verify the remote and branch, check overlapping peer changes, and retest integrated changes. Verify the remote commit ID after pushing. Include the purpose, stage commits, tests and remaining verification in the PR. Merge only after explicit authorization, required CI and review.
- Prepare Jira records as Korean drafts with the work performed, commit and PR links, tests, remaining work and a worklog note when applicable. Leave Jira updates to the assignee unless separately requested. Keep Smart Commits and Git-triggered Jira updates disabled.
